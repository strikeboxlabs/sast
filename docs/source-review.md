## SAST tool efficiency review, 2026-10-16

Independently verified the worker-evidence review above against the run artifacts. Confirmed: eight selection manifests, of which the seven analysis attempts i002-i008 carried all seven sast packages while i001's `general` profile carried none; zero scanner-name tool calls across all saved transcripts; metadata below the 6,000-token cap. One factual correction: recorded metadata estimates span 1,589-1,805 estimated tokens (i001 bootstrap = 1,805; i006 = 1,589; the others 1,700), so the recorded "about 1,589-1,700" understates the bootstrap maximum. Version checks for Semgrep 1.181.0, CodeQL 2.27.2 (csharp resolved) and Trivy 0.76.0 reproduced on this image.

Timed scanner results on the same checkout are recorded in the dated [validation](validation.md) entry. Efficiency reading: the manual Board dependency investigation (i007+i008: 2,217 s wall, 79 model calls, ~3.19M tokens) produced the same five-advisory list Trivy returned in 14.7 s from resolved `deps.json` inputs, and Trivy additionally surfaced two Dockerfile misconfigurations the manual run had copied as evidence but never analyzed (the report mentions the Dockerfile only in its evidence manifest). The manual run's decompilation differential, behavioral repro matrix and verified patch remain beyond scanner capability. Semgrep's C# value on this codebase was thin (one finding) and its parser partially failed on three production files; CodeQL extraction is viable only with toolchain provenance, failing in 2.9 s on the system SDK 6.0.400 and succeeding in 276.4 s via the prior run's recorded dotnet 9.0.319 — a live confirmation of the extraction reference's continuity guidance.

Routing consequence for this deployment: four of seven packages (bandit, brakeman, gosec, cppcheck) match no source language in this application, and the observed ~1.7k estimated tokens per attempt of injected-but-unused metadata bought no scanner use. The retained semgrep/codeql/trivy revisions address the failure modes actually observed (no recorded tool-selection decision, extraction provenance, advisory-severity versus application-impact separation).

Following this review, the same observed failures were folded back into the three applicable packages: Semgrep's entrypoint now requires quantifying `PartialParsing` coverage per language instead of listing errors (three production C# files partially parsed on 1.181.0); the CodeQL extraction reference names the NETSDK1045 fast-fail signature and the existing-database-directory refusal with its `--overwrite` recovery; the CodeQL entrypoint distinguishes cold query-compilation cost from scan cost (observed analysis outlasting extraction); and the Trivy category reference addresses multiple and possibly stale resolved inputs for one application (per-project and test-output `deps.json` copies). No scanner commands, scope, or authorization boundaries changed.
